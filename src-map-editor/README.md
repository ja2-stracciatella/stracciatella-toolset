# ja2-map-editor

Tactical map viewer and editor for Jagged Alliance 2 maps, built with [Bevy](https://bevyengine.org) 0.19. It is based on `ja2-next` and is compiled to WebAssembly. The toolset renderer runs it on a canvas in the "Tactical Maps" page. Bevy is used with a trimmed feature set (2D render and UI only, plus `webgpu` and `web`; see `Cargo.toml`). It needs WebGPU, because the map is drawn by a fragment shader that reads storage buffers. On Linux, `src/main/main.ts` enables Vulkan in Chromium for that.

## Building

The crate only targets `wasm32-unknown-unknown`. It is a member of the toolset's Cargo workspace, but not a default member, so plain `cargo build` in the repo root only builds the Neon addon.

```bash
npm run rebuild:map-editor            # release build + wasm-bindgen into src-map-editor/pkg (gitignored)
npm run rebuild:map-editor -- --dist  # smaller wasm with LTO (`wasm-dist` profile), used for packaging
cargo check -p ja2-map-editor --target wasm32-unknown-unknown
cargo clippy -p ja2-map-editor --target wasm32-unknown-unknown
cargo test -p ja2-map-editor          # unit tests run natively, they don't need JA2 data
```

The build needs the `wasm-bindgen` CLI in exactly the version pinned for the `wasm-bindgen` crate in `Cargo.toml` (`cargo install wasm-bindgen-cli --version <version> --locked`). The build script checks this. `rust-toolchain.toml` installs the wasm target.

The workspace dev profile builds this crate at opt-level 1 and all dependencies at opt-level 3, because Bevy is too slow without optimization.

## Architecture

**Host API (`src/lib.rs`)**: the `#[wasm_bindgen]` exports used by `src/renderer/lib/mapViewer.ts`:

- `start(canvasSelector, readFile, filesExist, onStatus, onEditorEvent)` builds and runs the Bevy app on the given canvas. `run()` returns immediately on wasm. It must only be called once per page, because winit can only create its event loop once. The toolset keeps the app alive and moves the canvas between the page and a hidden holder.
- `load_map(path)` queues a map (e.g. `maps/A9.dat`). `switch_map` in `states/loading.rs` picks it up in `PreUpdate`, removes the resources of the current map, replaces the scene with an empty one (which clears the baked regions), resets the camera position (the zoom is kept) and restarts `AppState::Loading`.
- `set_render_options(json)` sets the visible layers and day or night lighting (`RenderOptions` in `render/mod.rs`, see the doc comment in `lib.rs`). It is picked up in `PreUpdate` like `load_map` and kept when loading other maps.
- `set_active(active)` throttles updates (`WinitSettings`) while the viewer is not shown.
- `set_editor_mode(json)` sets the editing mode (`EditorMode` in `editor/mode.rs`, see the doc comment in `lib.rs`). Only the latest mode counts, and it is kept when loading other maps.
- `undo()`, `set_map_background(texture)`, `set_map_smoothing(type)`, `roof_all_rooms()`, `set_door(json)` and the commands of the soldiers, items, lights and traversal modes (`set_soldier`, `soldier_command`, `set_item`, `item_command`, `set_light`, `light_command`, `set_traversal`) are queued (`EditorCommand`), so none of them gets lost. Commands that arrive before a map is shown are dropped.
- `onEditorEvent` is called with JSON objects: `{ type: 'palette', map, tileset, ground, roads, cliffs, debris, trees, rocks, misc, buildings }` once a map is loaded (`buildings` has the palettes of the buildings mode, e.g. `room`, `walls` and `smartDoors`), where every palette entry is `{ tileId, tileType, typeName, subIndex, file, subImage }` (`editor/palette.rs`), `{ type: 'state', map, canUndo, undoDepth, background, nextRoomNumber, smoothing }` whenever one of these changes (`editor/commands.rs`), `{ type: 'door', map, gridNo, door }` when a door is clicked with the door locks tool (`editor/doors.rs`), `{ type: 'light', map, light, count, color, ambient, radii }` when the selected light or the lighting of the map changes (`editor/light_events.rs`), and `{ type: 'traversal', map, exitGrids, selected, queried, entryPoints, edgePoints }` when the exit grids, the entry points, the selected exit grid or entry point, the right clicked exit grid or the edge points change (`editor/traversal_events.rs`).
- `save_map()` resolves with the map file of the edited map (`editor/save.rs`), after generating the edge points again if edits made them out of date.
- `render_radar_map(map)` resolves with the radar map STI of the loaded map (`systems/radar.rs`, `render/radar.rs`): the map is drawn once more offscreen in the order and lighting of the game's map utility, read back, shrunk to 88×44 like the game does and reduced to a palette.

The TypeScript declaration of this API lives in `src/renderer/lib/ja2-map-editor.d.ts` and has to be kept in sync by hand.

**File access (`src/host.rs`)**: `HostPlugin` registers `HostAssetReader` as the `ja2://` asset source, and must be added before `DefaultPlugins`. It calls the JS `readFile(path)`, which resolves to a `Uint8Array` read with the `resources/read` invokable, or to `null` if the file does not exist (this becomes `AssetReaderError::NotFound`). That invokable reads the selected mod's files, with the vanilla data (via the stracciatella VFS) as a fallback. Examples are `ja2://maps/B13.DAT`, `ja2://binarydata/ja2set.dat`, `ja2://tilesets/<id>/<file>.sti` the optional structure data `ja2://tilesets/<id>/<file>.jsd`, the light templates (`ja2://L-R03.LHT`), the item files (`ja2://weapons.json` etc.), the soldier palettes (`ja2://binarydata/ja2pal.dat`) and the standing soldier animations (`ja2://anims/...`). `onStatus` is called with `{ state: 'loading' | 'loaded' | 'error', map, message? }`. The JS callbacks are not `Send`, so they are kept in a thread local (wasm is single threaded). The UI font is embedded with `include_bytes!` (`states/mod.rs`), so no assets are served.

**File formats (`src/file_formats/`)** are parsers for JA2 binary formats: map `.DAT`, the tileset definition file `JA2SET.DAT` (validated like the game: 50 vanilla or 70 Unfinished Business tilesets), structure data `.jsd` (`ja2_structure.rs`: aux data, tile locations, structures and z-strip info) and STCI (`stci/`: indexed/palette, RGB565/888, ETRLE). The STCI parser is a copy of the one in the `stracciatella` crate. The crate itself cannot be used here because it doesn't compile for `wasm32-unknown-unknown`: its `jsonschema` dependency uses `Url::to_file_path`. Each format is exposed as a Bevy `Asset` + `AssetLoader`, and all of them are registered in `Ja2AssetsPlugin`. `StciLoader` keeps an indexed STCI as it is: a `StciSheet` has the palette, the palette indices of every sub image and a `SubImageInfo` with offset, size and app data per sub image. RGB STCIs can't be drawn.

**Tile database (`ja2_tile_types.rs`, `ja2_tile_database.rs`)** is a port of the game's tile database (`TileDat.cc`, `TileDef.cc`). `ja2_tile_types.rs` has the tile type constants and tables (names, tiles per type, shadow buddies, door animations). Every tile type has exactly `NUM_TILES_PER_TYPE` entries, so the database index of a tile only depends on its type and sub index (`start(type) + sub_index - 1`, which spills into the next type when out of range, like in the game). `Ja2TileDatabase::build` takes one loaded surface (STI metadata + optional JSD) per tile type, cuts off extra sprites, pads missing ones with underflow fillers that show region 0, and computes the per-tile data: flags (wall, roof, a-frame, multi-z, animated, ...), terrain, wall orientation, fullness, shadow buddies, animation frames, structure and z-strips. The renderer and the lighting use it. `advance_animations` advances the animated tiles like the game's `ANIMATETILES` timer. `AssetMetaCheck::Never` is set because JA2 assets have no `.meta` files.

**State machine (`src/states/`)**: `AppState { Idle, Loading, Map }`, with sub-states `LoadingPhase { MapAndTilesets, TileSheets, Failed }` (under Loading) and `DebugOverlay { Off, On }` (under Map, toggled with F3). The app starts `Idle` until the host requests a map.

- `loading.rs` loads the map and `JA2SET.DAT`, then queues the STI sheet and the JSD file of every tile type, like the game. Each type falls back to the default tileset (0, or 50 with 70 tilesets) if the map's tileset has no file for it. A JSD that does not exist is not an error. It also loads the light templates of the map lights and the ones the editor places (`L-R01.LHT` to `L-R08.LHT`, kept as the `LightTemplates` resource), the item files and the soldier files (the standing surfaces and palette files come from the soldier registries); if one of these is missing, the lights, items or soldiers that need it are left out. When everything is loaded, it builds the `Ja2TileDatabase` and the `Tileset`, converts the map into a `TacticalMap` (see below), builds the level nodes (`MapWorld::build`), adds the items and soldiers, compiles the movement costs (which the lights need), inserts the `TacticalMap` resource and switches to `AppState::Map`.

**Runtime map (`src/map/`)**: `TacticalMap::from_ja2` converts the parsed `Ja2Map` into the `TacticalMap` resource once the tileset, the item files (`src/item/`), the light templates (`src/light/`) and the soldier palettes are loaded (`MapContext`). After that only `states/loading.rs` and `map/convert.rs` know about the file format. Grid numbers are `GridNo`s, which are always on the map (`NOWHERE` and invalid numbers become `None`), and per tile data is kept in `GridArray`s indexed by them. `GridNo::offset` is the game's plain grid number arithmetic, `GridNo::step` is `NewGridNo`. Tiles are `Arc<Tile>`s of the tileset, items, light templates, soldier definitions and palette replacements are resolved, the enums of the game (orders, attitudes, visibility, schedule actions, door traps, ...) are Rust enums, and the version specific fix-ups of the game (phantom menace structs, the ambient light of old caves maps) are applied. Anything that can't be converted is left out with a warning.

**Soldier definitions (`src/soldier/`)**: the game's teams, soldier classes, body types and standing animation surfaces are tables of structs (`Team`, `SoldierClass`, `SoldierBodyType`, `StandingSurface`) that carry their behaviour, e.g. whether a team is placed by the editor or hostile, the uniform of a class, and the standing animation, palette and vehicle flag of a body type. `SoldierPlugin` registers them as `Registry<T>` resources (`Teams`, `SoldierClasses`, `SoldierBodyTypes`, `StandingSurfaces`) when `AppState::Loading` is entered, before `start_loading` runs. A registry stores its definitions as `Arc<T>`, and everything that refers to a definition holds such an `Arc` (e.g. a body type's standing animation, a placement's team, a soldier's surface), so the body types are built from the registered surfaces. Every definition has an id, a newtype with a private field (`TeamId`, `SoldierClassId`, ...) with named constants for comparisons. Ids are dense (id `n` is at index `n`, which is also the index of a surface's sprite sheet). `Registry::validate` turns a raw number into the `Arc` of its definition. The map parser keeps the raw numbers. The map conversion (`map/convert.rs`) validates the placements against the registries. A placement with an unknown team, class or body type is skipped with a warning, and loading continues. `SoldierPlacement::index` keeps the index in the map file, so that skipping a placement does not change the random choices of the others. The game's random choices are made with a seeded `Random` (`src/random.rs`, a SplitMix64 generator that the editor uses as well) per placement (`placement_random` in `soldier/random.rs`). `choose_body_type` (`body_type.rs`) makes the first of them, the body type, and `soldier_palette` (`palette.rs`) continues with the same generator for skin, hair and clothes. The result is a `SoldierPalette`: the animation's own palette, a palette file, or the names of the `ja2pal.dat` replacements, which the conversion looks up in the loaded `PaletteReplacements` (`palette_files.rs`, `ResolvedSoldierPalette`). The renderer (`render/soldiers.rs`) only works with the converted placements; it picks the animation frame and applies the palette with the loaded files.

**Coordinates (`src/components/map.rs`)**: the map is 160×160 tiles (`GridPosition`, and `GridNo` `y * 160 + x`), and tiles are isometric 40×20 px. The renderer works in the game's screen pixels ("game pixels", y down), where the bounding box of tile (x, y) starts at `(20 * (x - y), 10 * (x + y))`. `game_to_world`/`world_to_game` convert them to Bevy world space (y up, the map center at the origin, every game pixel an integer unit square), and `game_to_tile` finds the tile under a position. The cursor, the bake regions and the debug overlay use these.

**Rendering (`src/render/`)** reproduces the game's software renderer pixel for pixel, with 8 bit colour channels instead of the game's 16 bit frame buffer. A pixel's colour only depends on the ordered list of blits that cover it, so:

- `world.rs` builds the level node lists of every tile in the order of the game's linked lists (`LoadWorld`, `WorldMan.cc`): land from the topmost full tile towards the head, buddy shadows of outdoor structs, and structure placement (`AddStructureToWorld`), which drops structs that overlap others like the game does.
- `items.rs` and `soldiers.rs` add the world items (to the struct and on-roof lists, `InternalAddItemToPool`) and the soldier placements (standing, first frame, with palette replacements; random choices of the game are made with a seeded generator).
- `reachable.rs` ports the reachable tests of `FindBestPath` (`PathAI.cc`) for the soldier the edge point functions use, including the order of its queue, which decides about the tiles behind fences, and its limits. `edge_points.rs` ports `GenerateMapEdgepoints` (`Map_Edgepoints.cc`) with it: the two diagonal rows of each side that are reachable from the first entry point (and not in a room on the surface), the secondary set reachable from the isolated entry point, the removal of the edge points that can't reach the edge of the map and the classification against the entry points, with the quirks of the middle indices and the larger range of I14. With the game data in `JA2_DATA_DIR`, a test compares the generated edge points with the ones of the maps of the game (222 of the 261 vanilla maps match exactly; the others were changed after their edge points were saved, and I14 was saved without its special case).
- `movement_costs.rs` (`CompileTileMovementCosts`, `DoorTravelCost`) and `lighting.rs` (`LightSetBaseLevel`, `LightDraw`, `IlluminationFilter`) compute the shade level of every node for day (ambient 3) or night (ambient 12, with the night lights on). Static shadows are only drawn below ambient 8. The nodes of the `MapWorld` resource are lit in place (`light_all`: `base_light` for every tile, then `draw_light` for every light that is on). Lights combine by their maximum, so drawing a light again changes nothing.
- `draw_list.rs` ports `RenderTiles`: the passes of `RenderStaticWorld` and `RenderDynamicWorld`, row by row with the layers of a pass interleaved per row, and per node the position, z value (16 bit, with the game's `INT16` wrap) and blitter (`Blitter`). Because of this order, the draws of the map are sorted by pass, row, layer, x and node, so the draws of every tile can be computed on their own (`DrawContext::tile_draws`, with a key for that order). `DrawCache` keeps them per tile: `all()` is the draw list of the map, and `ordered(rect)` the draws that overlap a rectangle, in the same order, which produce the same pixels in that rectangle.
- `regions.rs` splits the area that the map can cover (`map_bounds`) into regions of at most 512×512 px (`RegionLayout`). Each region has its own draws: the draws that overlap it, in draw list order.
- `bins.rs` sorts the draws of a region into 32×32 px bins, and `atlas.rs` packs them into `u32` storage buffers (`RegionScene`). The used sprites (as palette indices), the shaded palettes (`palette.rs`) and the animation table are shared by all regions (`SceneAtlas`). The atlas only grows, so the draws of a region stay valid when other regions add sprites.
- `shaders/ja2_replay.wesl` (`replay_material.rs`, a `Material2d`) starts every pixel with the clear colour and z 0 and applies the draws of its bin with the depth rules of each blitter. `reference.rs` is the same function on the CPU, for tests.

`update_scene` brings the scene (`ReplayScene`: the shared buffers and one `RegionScene` per region, each with a version) up to date with the changes in `PendingSceneUpdate`. Loading a map and changing the render options request a full rebuild. Edits add the tiles whose level nodes changed (`MapWorld::sync_tiles`), and the update only redoes what they affect: `MovementCosts::recompile_area` compiles the costs around them again, `relight_area` relights the lights that reach them, `DrawContext::tile_draws` recomputes the draws of these tiles, and only the regions that the old or new draws overlap are built again. Each of these steps gives the same result as doing it for the whole map, which `render/tests.rs` checks with random edits. Above 4000 changed tiles everything is rebuilt. The update waits until the bake is idle (`MapBake::is_idle`), because the bake waits for the materials of every change; updating while it waits would delay it again and again. Changes that arrive in the meantime are handled together. What the scene was built from (the `DrawCache`, the `SceneAtlas` and the lighting) is kept in `SceneSources`. Animated tiles only update a small buffer of current frames every 200 ms.

**Baking (`systems/bake.rs`)**: replaying the draws for every pixel is too expensive to do every frame. Every region of the `RegionLayout` has a texture (even sizes, integer centers), a quad with its replay material on render layer 2 and a bake camera that renders the quad into the texture. Storage buffers and materials are never modified; every change creates new ones, and the bake cameras only run once the render world reports that the new materials (including those of an earlier generation that was not ready yet) are prepared and no pipeline is compiling (`ReadyReplayMaterials`), so a region is never cleared by an unfinished bake. Only the buffers of regions whose version changed are uploaded, and only these regions are baked again. New shared buffers or animation frames replace the materials of all regions without baking them, except that animation updates bake the regions with animated draws. `warn_about_draws_outside` warns when draws reach outside of the baked area.

**Rendering pipeline (`systems/pixel_view.rs`)**: the world camera (`TileCamera`, render layer 0) renders the baked regions into an off-screen texture at exactly 1 world px = 1 texel, with MSAA off and from an integer position, so the nearest-sampled region sprites can't leave gaps between each other. The texture is sized for the window at the minimum zoom and has no CPU-side data. The world camera renders into a centered `Camera.viewport` that fits the current zoom, and the screen sprite shows that part (`Sprite.rect`). This way, the texture only changes size with the window: Bevy sees a resized render target one frame late, which would distort the image for a frame while zooming. The screen camera (`ScreenCamera`, render layer 1, 1 unit = 1 physical px) draws the texture as a single bilinear filtered sprite, scaled by the zoom and shifted by the sub-pixel part of the camera position, so scrolling and zooming stay smooth. The UI is rendered by the screen camera at screen resolution. The view (`PixelView`: world position at the screen center, zoom in physical px per world px) is the source of truth for the camera. `systems/camera.rs` moves and zooms it and keeps it inside the part of the map that the game can scroll over plus a margin (`scrollable_area` in `render/movement_costs.rs`, which depends on `ubRestrictedScrollID`), and `screen_to_world` converts the cursor into world coordinates. Gizmos render into the texture along with the map.

**Editing (`src/editor/`)** ports the terrain, buildings, soldiers, items, lights and traversal modes of the original editor (`src/game/Editor/` of the game). The document is the `TacticalMap`: every edit changes its tile layers through an `EditContext` (`document.rs`), which records the tile for undo, and `commit` syncs the world with `MapWorld::sync_tiles` and collects the touched tiles for `PendingSceneUpdate`. Structures are committed right away, so the next placement of the same brush sees them. The `EditContext` helpers are ports of the `WorldMan.cc` functions, e.g. `set_land_index` (the head of `MapTile::land` is its last element, the heads of the other layers are their first elements, see `MapTile`). The game sets the logical heights of all tile types to 1 before the editor runs, so the code for "higher" land is left out.

- `smooth.rs` has the smoothing tables of `Smooth.cc`, which pick the edge tile of a texture from which of its neighbours have it (water looks at all 8 neighbours).
- `ground.rs` paints textures (`PasteTextureCommon`), fills areas (a breadth first search instead of the recursion, which could never end), erases the topmost texture and sets the background texture of the whole map.
- `cliffs.rs` places the cliff pieces with their overhanging edges (`PasteBanks`) and sets the height of the tiles from the cliffs of the map after every cliff edit, a port of `RaiseWorldLand` that the original ran when saving. The pieces are picked by hand, the original has no cliff smoothing.
- `roads.rs` has the road macro table of `Road_Smoothing.cc`, `placement.rs` the palettes of `SelectWin.cc`, the weighted random selection and placing and erasing debris and structures.
- `walls.rs` places wall pieces for a floor tile and fixes up the corners they make (`BuildWallPiece`), and has the wall helpers of `Smoothing_Utils.cc`. A horizontal wall stored on a tile is on its edge to the next row, a vertical one on its edge to the next column, so the top and left walls of a room are stored on the tiles above and left of it. `building.rs` adds and saws rooms, kills buildings and rebuilds roofs (`NewSmooth.cc`, `EditorBuildings.cc`). A room whose materials have a slant roof but no flat roof gets a slant roof with A-frames, which is 8 tiles wide, so the room tool forces a line brush of that width. What the editor needs to know about building tiles (the wall piece, door state, roof piece, style, ...) is the `building` attribute of the `Tile`, set when the tileset is built, and the wall orientations come from the tile database.
- `caves.rs` fills areas with rock and carves caves out of it on cave maps: the rock piece of a tile follows which of its 8 neighbours are rock (the perimeter table of `NewSmooth.cc`). The map file doesn't know which walls are rock, so `MapTile::cave` marks the pieces the editor placed, and the pieces surrounded by rock are marked when a cave map is loaded. Basements are rock made of floors and roofs, the building functions carve rooms out of it (`is_basement`). The map type is `MapInfo::editor_smoothing`, which `set_map_smoothing` changes.
- `soldiers.rs` is the soldiers mode (the Mercs tab of the original): the place tool places a soldier of the mode's team with the mode's defaults with a left click, on flat roofs if the mode or Page Up says so, or erases the soldiers of the shown teams on the tiles of the brush, with their schedules. The select tool selects the clicked soldier (clicking it again selects the next soldier of the tile), dragging moves it and Ctrl+dragging copies it (with its team, values, detailed placement and patrol, but without its schedule), both keep its level. Delete removes it, 1 to 9 set its patrol points (Shift removes them). The host edits the selected soldier, its detailed placement and its schedule (`soldier_events.rs`, `schedules.rs`). `soldier_overlay.rs` draws the markers, the patrol points and the slot, name and patrol warnings of the shown soldiers.
- `items.rs` is the items mode (the Items tab of the original): the place tool places the chosen item, trigger, action item or key with the defaults of the original with a left click, or erases the items shown on the tiles of the brush. The select tool selects the clicked tile with all items shown on it (its pool, which can be the base tile of the structure the items lie on), dragging moves them and Ctrl+dragging copies them, both keep their levels and refuse items that would sink in water or a second trigger on the tile. Delete removes all items of the tile. The host lists the items of the selected tile, edits them and removes single ones (`item_events.rs`). `item_overlay.rs` draws a ring on every tile with items, the selected tile and the pits of its action items.
- `lights.rs` is the lights mode (the lights of the Map Info tab of the original): the place tool places a light of the mode's radius (the template `L-R0N.LHT`) and time (prime time, night or always) with a left click, replacing the lights of the tile, or erases the lights of the tiles of the brush. The select tool selects the clicked light (clicking it again selects the next light of the tile), dragging moves it and Ctrl+dragging copies it, Delete removes it. The host edits the selected light, the light colour and the light level of basements and caves (`light_events.rs`, the level is 16 minus the ambient level). `sync_light_scene` relights the tiles that the changed lights reach (`light_tiles`); a new light colour or ambient level rebuilds the scene, because the shaded palettes and the base light of every tile depend on them. `light_overlay.rs` draws a ring on every light in the colour of its time. Saving writes the lights of the map file again: unchanged lights keep their record, the ones that could not be converted are kept, and the ambient light is only written when it differs from the file's (old caves maps use another level in the game than the saved one). Like in the original, only basements and caves have an ambient light: the map type sets it (`set_smoothing`), maps that become basements or caves start with level 12 (ambient 4) or keep theirs, and maps that become normal lose it, also in the saved file.
- `traversal.rs` is the traversal mode (the exit grids and entry points of the Map Info tab of the original): the place tool paints exit grids to the mode's destination with square brushes or areas (`DRAW_MODE_EXITGRID`), replacing the ones of the tiles, a right click reports the clicked exit grid so the host can copy its values, and a left click sets the chosen entry point, moved into the area the game can show (`ValidateEntryPointGridNo`). The select tool selects, moves and deletes entry points and exit grids and copies exit grids, like the lights mode does with lights. `sync_traversal_scene` compiles the movement costs of the changed exit grids again. The edge points are derived data: the edits that can move them (tiles, which includes rooms, exit grids, entry points, the map type and door locks) set `EditorDocument::edge_points_dirty`, and `regenerate_edge_points` generates them again (`render/edge_points.rs`) once the movement costs caught up, while the traversal mode is shown and before saving. Undo only marks them again. They are only saved when they were generated again (`TacticalMap::edge_points_stale`), so untouched maps keep their edge points byte for byte. `traversal_overlay.rs` draws the exit grids, the entry points with their letters and, with the select tool unless an exit grid is selected, the edge points, the ones of the selected entry point highlighted (both sets of its side, the secondary sets for the isolated one, none for the center one).
- `doors.rs` edits the door table: clicking a door or another openable structure with the door locks tool reports a `door` event, the host shows a dialog and sets the lock and trap with `set_door`. Undo keeps the door table of a command. The doors of the table get a key marker while the tool is active.
- `layout.rs` copies and moves buildings: the layout is the tiles of the floors and roofs and the walls around them, the tiles are copied in an order that never overwrites a tile before it is copied. Moved buildings leave the background texture behind, where the original leaves tiles without land. The tools drag with `Brush::Drag`, the tile where the mouse is pressed and where it is released, and the brush cursor shows the layout where it goes.
- `scroll_area.rs` draws the part of the map that the game can scroll over as a white box with gizmos, and rebuilds the scene and the movement costs when the host changes the scroll restriction (`set_restricted_scroll`), because the visible tiles and the z values depend on it.
- `rooms_overlay.rs` shows the room numbers of the tiles in view as text on the screen camera when the `roomNumbers` layer is on. That layer and the room numbers are not part of the scene, toggling it doesn't rebuild it.
- `smart.rs` is the smart method (`SmartMethod.cc`): walls that pick vertical or horizontal pieces from the walls around them, and doors, windows and broken walls that replace the walls of a tile. They are looked up by their building piece and the orientation of the wall, instead of the original's sub index arithmetic, which has been wrong since the orientations became bit flags.
- `building_mode.rs` is the buildings mode: the tools, how they restrict the brush (`EnsureSelectionType`), placing single tiles in their layers (`PasteSingleWallCommon`), erasing them (`EraseMapTile`) and the right button of the smart tool.
- `brush.rs` has the brushes (square and circle up to 15×15, line and area) and the density test, `mode.rs` the mode from the host and how it is applied to the tiles of the brush. `undo.rs` keeps the first state of every changed tile per stroke, and the background, the map type and the door table if the stroke or command changed them, for the last 10 strokes. Commands of the soldiers, items, lights and traversal modes keep the whole list they changed (the entry points of the map info).
- `input.rs` paints while a mouse button is held (the right one only for the tools that use it): the brush is applied once to every tile the cursor enters (and to the tiles in between, so fast strokes have no gaps), the line and area brushes when the button is released. It also draws the brush cursor with gizmos. `preview.rs` shows tinted sprites of what the next click places or removes: the objects with a copy of the random numbers, the roads, the cliffs, and the single tile and smart building tools with a dry run that applies the tool, collects the changed tiles and undoes it again. `commands.rs` applies the mode and the commands of the host and reports the state of the editor, `palette.rs` reports the palettes.

Some bugs of the original are fixed: the road macros replace the road pieces of the tiles they go to, debris only replaces debris, weighted textures are picked without bias, fills always end, adding a room to a building whose land head is not a floor ends, broken walls replace the wall of their own alignment, and every edit (including erasing roads and setting the background) can be undone.

**System ordering**: every per-frame map system goes into one of the chained `MapSystems` sets (`Scene → Input → Camera → View → Cursor → Edit → Debug`), configured in `systems/mod.rs`. The loading pollers run `.before(MapSystems::Scene)` so the scene systems see a complete map. New systems should join the appropriate set. Every feature is a `Plugin` registered in `lib.rs`.

`lib.rs` allows `clippy::too_many_arguments` and `clippy::type_complexity` crate-wide because Bevy systems need them.

## Controls

| Key                      | Action                     |
| ------------------------ | -------------------------- |
| W / A / S / D            | Move the camera            |
| Mouse at the canvas edge | Move the camera            |
| Mouse wheel / + / -      | Zoom                       |
| F3                       | Toggle tile debug overlay  |
| Left mouse button        | Paint with the editor mode |
| Left mouse drag          | Move the selected building, soldier, items, light, entry point or exit grid with the select tools, Ctrl+drag (Cmd+drag on macOS) copies them (except entry points) |
| Right mouse button       | Remove or restore walls with the smart building tool, copy the values of an exit grid when placing exit grids |

The canvas only receives keyboard input while it is focused. Therefore the toolset forwards the keys pressed elsewhere on the page with `key_event` (except while typing into an input) and releases them with `release_keys` when the page loses the focus or the viewer is hidden.
